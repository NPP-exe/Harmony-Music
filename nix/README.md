# Nix packaging

The flake supports `x86_64-linux` (Linux amd64). Enable the `nix-command` and
`flakes` experimental features in Nix. Run the following commands from the
repository root:

| Command | Result |
| --- | --- |
| `nix build` | Build the pinned stable release; the executable is `result/bin/harmonymusic` |
| `nix run` | Run that stable release |
| `nix build .#development` | Build the current checkout |
| `nix run .#development` | Run the current checkout |
| `nix develop` | Enter the Linux Flutter development environment |
| `nix run .#resolve-lockfile` | Resolve development dependencies and generate their Pub and Nix locks |
| `nix run .#update-lockfile` | Export the existing development Pub lockfile and record Git dependency hashes |
| `nix run .#update-release` | Update the stable release pin and its dependency locks |
| `nix flake check` | Build both packages, test maintenance safeguards, and check formatting, Nix workflows, and the development lockfile export |
| `nix fmt` | Format the Nix expressions |

To run the stable package without cloning the repository:

```sh
nix run github:NPP-exe/Harmony-Music
```

The package is also exported as `packages.x86_64-linux.harmonymusic`.

## Stable release policy

`nix/release.json` fixes a published stable tag, its commit, and its source hash.
The default package fetches those sources instead of building `main`. Updating
the checkout or changing the development lockfile does not change the stable
package. Changes to the packaging, its stable dependency lock, or nixpkgs can
still require a rebuild. Nix reuses unchanged dependencies; a binary cache for
the application is optional and is not configured by this flake.

`nix/release/pubspec.lock.json` records the resolved dependency set used by Nix.
It is generated from the release manifest and may differ from the tagged Pub
lockfile if that file needs resolution. The updater does not modify the tagged
sources or the checkout's `pubspec.lock`. Each exported lock has a companion
`git-hashes.json` recording the URL, revision, and content hash of Git dependencies.

Flutter is fixed to the nixpkgs `flutter329` package (currently 3.29.3, Dart
3.7.2 in the pinned nixpkgs revision). Keep the Flutter package choice, the release
manifest, and the resolved dependency lock compatible when updating.

The Nix packages disable automatic release checks. The manual update check in
the application's settings remains available; update the installed Nix package
through your Nix configuration or profile.

## Development

`nix develop` supplies Flutter with Linux artifacts, Clang, CMake, Ninja,
pkg-config, GTK 3, Ayatana AppIndicator, libmpv, and JDK 17. JDK 17 is needed
because the JNI plugin compiles a native library on Linux.

When entered from the project root, the shell prepares
`.dart_tool/package_config.json` using the dependencies patched by Nix. The
application and the vendored YouTube package still point to the checkout so
edits and hot reload work. Run `flutter run -d linux` to generate plugin
registration and start the app; Flutter recognizes the dependency configuration
generated by Nix and skips Pub resolution. `harmony-configure` can prepare it
again manually.

Before writing the configuration, it compares `pubspec.lock` with the resolved
lock embedded in that shell. If they differ or cannot be read, it reports an
error and leaves the existing configuration untouched. Resolve the locks and
re-enter the shell before continuing. The shell protects its store dependencies
from garbage collection while active; the local JSON alone does not retain them
after the shell exits.

After changing the development manifest, resolve Pub dependencies and update
their Nix exports with one command:

```sh
nix run .#resolve-lockfile
```

Review the manifest, Pub lockfile, `nix/pubspec.lock.json`, and `nix/git-hashes.json`
together. Re-enter `nix develop` to restore the patched plugin configuration after
Pub has written its own configuration. You can also export an already resolved
lockfile with `nix run .#update-lockfile`. To verify that export and its Git hash
records without downloading anything or changing files, run:

```sh
nix run .#update-lockfile -- --check
```

Git-backed flakes include files tracked by Git. Add newly created application
source files and packaging files to Git before building with them.

## Updating the stable release

After a stable GitHub release has been published, run from the project root:

```sh
nix run .#update-release
nix flake check
git diff -- nix/release.json nix/release/
```

The updater rejects drafts and prereleases, resolves the tag to a commit,
prefetches its source hash, resolves Pub dependencies in a temporary copy, and
updates only `nix/release.json` and `nix/release/`. It does not update nixpkgs or
the checkout's Pub lockfile. Updating requires network access. Package builds
use the recorded hashes and may download pinned sources and cached dependencies.

The command selects GitHub's latest published stable release. To select a
specific published stable release, pass its tag as
`nix run .#update-release -- TAG`. Explicit selection can also select an older
release. The tag must match the manifest version, with an optional `v` prefix.
Repeating an already pinned tag leaves the locks unchanged; use `--force` to regenerate its
dependency set intentionally, for example after a Flutter toolchain change.

## Toolchain and native dependencies

To update the toolchain separately, run `nix flake update nixpkgs`, review
`flake.lock`, and run `nix flake check`. If the new nixpkgs revision removes
`flutter329` or introduces incompatible changes, migrate the Flutter selection
and resolve the development and release locks before merging. Select a new
Flutter series in both `nix/package.nix` and `flake.nix`.

The native `audiotags` library is built from the Rust sources in its exact
pub.dev archive. The upstream archive omits its test samples, so those Rust tests
are disabled. Its Cargo dependencies are fixed in `nix/audiotags/Cargo.lock`.
When changing the plugin version, regenerate that Cargo lock from its Rust
manifest and update the version guard in `nix/audiotags.nix`. Review its CMake
and FFI patches against the new sources: the CMake binary download is removed
and the Linux FFI loader points to the compiled library inside the Nix store.
Both adaptations are confined to the Nix dependency derivation.

## Automated maintenance

The `Nix maintenance` workflow proposes updates in separate pull requests.
The workflow must be present on the repository's default branch, and GitHub
Actions must be enabled:

| Trigger | Proposed change |
| --- | --- |
| A stable release is published | Pin GitHub's latest stable release and resolve its release dependency locks |
| A development manifest or Pub lockfile changes on `main` | Resolve the checkout's Pub dependencies and synchronize its Pub and Nix locks |
| Monthly, on the first day at 05:23 UTC | Update the nixpkgs input in `flake.lock` |
| Manual workflow dispatch | Run any of these operations, optionally specifying a stable tag |

Each operation reuses its own `automation/nix-*` branch and pull request. If the
generated files already match the base branch, no new pull request is needed.
Updates to application releases, development dependencies, and nixpkgs remain
separate so they can be reviewed and reverted independently.

Concurrency groups follow the operation, including manual dispatches. A release
and a lockfile update cannot replace each other's pending execution. Multiple
pending requests for the same operation are coalesced to the newest request.

Preparation runs with read-only repository permissions. A separate publishing
job downloads the generated data, checks an exact file allowlist, rejects
symbolic links, and creates the PR without running Nix or Flutter. If the default
branch changed after preparation, publication fails and maintenance must be
rerun. All Actions in the Nix workflows are pinned to full commit SHAs.

The maintainer must enable **Settings > Actions > General > Workflow permissions >
Allow GitHub Actions to create and approve pull requests**. This setting permits
the bot to create PRs; the workflow does not approve or merge them. GitHub
documents this setting in its [Actions settings guide](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).

The workflow uses the repository's `GITHUB_TOKEN` and explicitly dispatches
`nix.yml` for the proposed branch. The Nix CI builds both packages, runs the
maintenance regression tests, and checks formatting, workflow syntax, and the
development lockfile export. This uses GitHub's supported
[`workflow_dispatch` mechanism](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)
without requiring a personal access token. Other PR workflows may still need a
maintainer to approve their runs under GitHub's bot-PR policy.

The publishing job needs `contents: write` to push the update branch,
`pull-requests: write` to open the PR, and `actions: write` to dispatch its checks.
The preparation job only has `contents: read`. The `tag` input applies only to
the manual `release` operation; leaving it empty selects latest. In the Actions
tab, use **Nix maintenance > Run workflow** to request or retry an operation.

Review and integration, Flutter series migrations, native plugin adaptations,
and graphical/audio verification remain maintainer tasks. An incompatible
update produces failing checks on its PR; it does not update the default
branch automatically.

## NixOS and Home Manager

Add the flake as an input to your configuration:

```nix
inputs.harmony-music.url = "github:NPP-exe/Harmony-Music";
```

Then include `inputs.harmony-music.packages.x86_64-linux.default` in
`environment.systemPackages` (NixOS) or `home.packages` (Home Manager). Your
configuration's `flake.lock` fixes the revision of this packaging as usual.
Updating that input picks up newly pinned stable releases.

Keep this flake's nixpkgs input pinned independently. Overriding it with
`inputs.harmony-music.inputs.nixpkgs.follows = "nixpkgs"` makes Flutter and native
dependency compatibility depend on your configuration's nixpkgs revision and
requires separate validation.

## Runtime verification

Besides the build checks, test application startup from the desktop menu and a
different working directory, audio playback, MPRIS controls, the tray menu,
file selection, downloads with metadata, and both X11 and Wayland sessions.
Live YouTube streaming and desktop integration require a graphical session and
network access and are not exercised by the sandboxed builds.
